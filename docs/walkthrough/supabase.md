# Supabase & Postgres, in depth

[Supabase](https://supabase.com/) is an open-source backend: **a real
Postgres database** with services bolted on (Auth, a generated REST API,
Realtime websockets, Edge Functions). This chapter teaches you the
Postgres and Supabase you need for this repo — **every concept below is
used in our migrations or frontend**, with a file reference for each.
(Why Supabase over the alternatives is a decision record:
[`dr-002-backend.md`](../drs/dr-002-backend.md).)

## 1. Postgres: tables, rows, columns

Postgres is a relational database: data lives in **tables** of **rows**,
each row having the **columns** the table declares. Our schema (the set of
tables) is defined entirely by the SQL files in
[`supabase/migrations/`](../../supabase/migrations/), applied **in filename
order**. To change the database you add a *new* migration file — you never
edit an old one, because other environments (teammates' machines, CI,
production) have already applied it.

The main tables: `profiles`, `households`, `household_members`,
`household_invites`, `meal_plans`, `meal_ideas`, `meal_plan_ingredients`,
`ingredients`, `day_placeholders`, `day_contexts`, `todo_items`,
`reactions`, `meal_outcomes`, `public_stats`, plus three tables for the
ChatGPT plugin's OAuth flow.

## 2. Declaring a table

Every migration starts with `create table`. Here's a real one —
[`20260402000003_meal_plans.sql`](../../supabase/migrations/20260402000003_meal_plans.sql):

```sql
create table public.meal_plans (
  id uuid primary key default gen_random_uuid(),
  household_id uuid not null references public.households(id) on delete cascade,
  date date not null,
  title text not null,
  description text,
  created_by uuid references public.profiles(id),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

Reading it line by line:

- **`id uuid primary key default gen_random_uuid()`** — every row gets a
  [UUID](https://en.wikipedia.org/wiki/Universally_unique_identifier) (a
  128-bit random id), generated by Postgres on insert. Primary keys are how
  every other table refers to this row. We use UUIDs rather than
  auto-incrementing integers so ids can be created anywhere without
  coordination and leak nothing about table size.
- **`not null`** — the column must always have a value. `description`
  lacks it, so it may be `null` — which is exactly why its TypeScript type
  is `string | null`.
- **`references public.households(id)`** — a **foreign key**: this column
  must contain the `id` of a real row in `households`. Postgres enforces
  it; you cannot insert a meal plan for a household that doesn't exist.
- **`on delete cascade`** — if the referenced household is deleted, its
  meal plans go with it. (Used across the schema so deleting a household
  cleans up all of its data — see
  [`20260428000001_delete_household_and_account.sql`](../../supabase/migrations/20260428000001_delete_household_and_account.sql).)
- **`timestamptz … default now()`** — timestamp-with-timezone columns that
  Postgres fills in automatically.
- **`date`** — a calendar date with no time component; perfect for "which
  day is this meal planned for".

Immediately after the table you'll always see:

```sql
alter table public.meal_plans enable row level security;
```

That switches on RLS — see §6. **Every table in this repo has it.**

## 3. The other DDL verbs we use

- **`alter table … add column`** — evolve an existing table, e.g.
  [`20260506000001_todo_items_note.sql`](../../supabase/migrations/20260506000001_todo_items_note.sql)
  adds a `note` column to `todo_items`.
- **`create index` / `unique`** — speed up lookups and enforce
  uniqueness. Example: `household_invites.token` is
  `uuid unique not null default gen_random_uuid()` in
  [`20260402000002_households.sql`](../../supabase/migrations/20260402000002_households.sql)
  — the database itself guarantees no two invite links share a token.
- **`check (...)`** — constrain values at the database level.
  [`20260510000001_meal_outcomes.sql`](../../supabase/migrations/20260510000001_meal_outcomes.sql)
  uses a CHECK to guarantee a missed meal **must** record a reason — a
  rule no buggy UI can bypass, because Postgres enforces it.
- **`create or replace function` + `create trigger`** — Postgres can run a
  function automatically when rows change. Real example from
  [`20260402000001_profiles.sql`](../../supabase/migrations/20260402000001_profiles.sql):

  ```sql
  create trigger on_auth_user_created
    after insert on auth.users
    for each row execute function public.handle_new_user();
  ```

  When someone signs up (a row appears in Supabase's `auth.users` table),
  the trigger fires and `handle_new_user()` creates their `profiles` row
  and personal household automatically.
- **`security definer`** — a function that runs with the *definer's*
  permissions rather than the caller's. We use it sparingly for operations
  RLS would otherwise block, e.g. the cached global-stats functions in
  [`20260510000002_public_stats.sql`](../../supabase/migrations/20260510000002_public_stats.sql),
  which also schedule a daily refresh via **pg_cron** (a Postgres job
  scheduler).
- **`alter publication supabase_realtime add table …`** — opts a table
  into realtime broadcasts; all of them live in
  [`20260402000006_realtime.sql`](../../supabase/migrations/20260402000006_realtime.sql).

## 4. Auth

`supabase.auth.signUp({...})`, `signInWithPassword({...})`, etc., wrapped
in [`src/hooks/useAuth.tsx`](../../src/hooks/useAuth.tsx). Sign-in returns
a **JWT** (a signed token) that the JS client automatically attaches to
every subsequent REST and Realtime call. Inside the database, the policy
function `auth.uid()` reads the user's id out of that JWT — that's the
bridge between "who is logged in" and "which rows may they touch". Auth
is the only REST-only flow: the token must exist before the WebSocket can
connect.

## 5. PostgREST: the schema *is* the API

When you call `supabase.from('meal_plans').select(...)`, the JS client
builds a URL, Supabase's PostgREST server turns it into SQL, and Postgres
answers. **You don't write API routes.** The `select` syntax also supports
joins:

```ts
supabase.from('meal_plans')
  .select('*, meal_plan_ingredients(*, ingredients(*))')
```

means "every column of `meal_plans`, plus for each row every joined
`meal_plan_ingredients` row, plus the `ingredient` row each of those
points at" — a SQL join expressed as a nested select. Filtering is
chained: `.eq('household_id', householdId).gte('date', start)` becomes
`WHERE` clauses.

## 6. Row-Level Security (RLS): where authorisation lives

RLS policies are SQL rules, attached to a table, that Postgres applies to
**every** query: "this user can read/write this row if and only if …".
They run in the database, so even a hand-crafted malicious request can't
get past them. Real examples from
[`20260402000005_rls_policies.sql`](../../supabase/migrations/20260402000005_rls_policies.sql):

```sql
-- You may only ever see your own profile row.
create policy "Users can view their own profile"
  on public.profiles for select
  using (auth.uid() = id);

-- You may see a household iff a household_members row links you to it.
create policy "Members can view their households"
  on public.households for select
  using (
    exists (
      select 1 from public.household_members
      where household_members.household_id = households.id
      and household_members.user_id = auth.uid()
    )
  );
```

- **`for select`** — which operation the policy governs (there are also
  `for insert`, `for update`, `for delete`).
- **`using (...)`** — the check applied to each candidate row. `exists`
  is a subquery: "true if at least one matching row exists".
- **`auth.uid()`** — the caller's user id, from their JWT (§4).

The policies mirror the role predicates in
[`src/lib/permissions.ts`](../../src/lib/permissions.ts) — the UI and the
database must always agree. Anonymous public-share access is its own
carefully-audited surface; see [`docs/public.md`](../public.md).

## 7. Realtime

Supabase Realtime is a WebSocket server that broadcasts Postgres
`INSERT`/`UPDATE`/`DELETE` events for tables added to the
`supabase_realtime` publication (§3). The client subscribes per
household and feeds events into the TanStack Query cache — the full
mechanics are in [TanStack Query & Realtime](tanstack-query-and-realtime.md).

## 8. Edge Functions

Two Deno functions in
[`supabase/functions/`](../../supabase/functions/) (`chatgpt-plugin`,
`chatgpt-plugin-auth`) implement the OAuth flow that lets ChatGPT act on a
household's behalf. Setup guide: [`docs/chatgpt-plugin.md`](../chatgpt-plugin.md);
testing them locally: [`docs/edge-functions-testing.md`](../edge-functions-testing.md).

## 9. Running it locally

```bash
npx supabase start     # boots Postgres + Auth + Realtime + Storage + Kong in Docker;
                       # applies every migration in supabase/migrations/ on first boot
npx supabase db reset  # tears down and re-applies all migrations from scratch
```

Everything is **household-scoped**: a user can belong to several
households, and each household's data is isolated by the RLS policies
above.
